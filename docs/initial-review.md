# Анализ Umbra: стабильность, авторизация и сохранность данных

Проверена версия `f68f42c1a6a7ed39dc189dcfb46fa37bf8aaa12d`, полученная из репозитория https://github.com/kovalenkoserhii2107-maker/umbra. Проанализированы все исходные модули `src`, настройки TypeScript/Vite/PWA, HTML, workflow публикации и документация. Код приложения не изменён. Дата окружения: 26 сентября 2026.

**Вывод:** React + TypeScript + Firebase подходят этому проекту. Основные препятствия надёжности — несколько источников состояния авторизации, смешивание данных пользователей, неполная синхронизация и два способа запуска/публикации приложения. Переписывать весь интерфейс или менять Firebase для исправления этих проблем не требуется.

## Что проверено исполнением

- Установка зависимостей: `npm install --ignore-scripts --package-lock=false` в отдельном временном клоне. Lock-файла в репозитории нет. Аудит установленного дерева npm сообщил 0 известных уязвимостей; это не оценка безопасности приложения.
- `npm run build` успешно: TypeScript и production-сборка. Локальная среда Node 24.19.0; workflow задаёт Node 22, поэтому это не идентичное воспроизведение CI.
- Получен JS размером 874,31 kB, gzip 263,29 kB. Есть предупреждение о размере и о ссылке на `/umbra/assets/index.css?v=0.5.4`.
- Вызов Firebase SDK с `season: undefined` на фиктивной конфигурации локально отклонён с `invalid-argument: Unsupported field value: undefined`. Данные в рабочий Firebase не отправлялись.
- Исполнение извлечённого `listenAuth` с подменённым Firebase callback подтвердило: событие `user = null` оставляет прежний сохранённый профиль.
- Исполнение исходной `mergeLibraries` подтвердило: локальная запись остаётся при пустой удалённой библиотеке. Это объясняет и перенос между аккаунтами, и восстановление удалённых записей.
- Получен HTML опубликованного сайта. Он содержит исходный `/src/main.tsx` и обходной загрузчик `/umbra/assets/index.js?v=0.5.4`. Запрос исходного файла вернул HTTP 404.
- В локальном `dist/index.html` есть одновременно стандартный entry `/umbra/assets/index.js` и обходной entry с query-параметром. Это разные URL модулей.

Полноценный вход реальным аккаунтом, сценарии на двух устройствах и Safari/PWA не выполнялись. Правила Firestore, настройки OAuth, список разрешённых доменов, квоты и журналы Firebase из репозитория неизвестны. Ниже явно разделены подтверждённые дефекты кода и вопросы инфраструктуры.

## 1. Перенос личных данных между аккаунтами — исправить первым

**Код:** `src/state.tsx:29, 77–108, 126–129`; `src/lib/auth.ts:103–105`.

Все пользователи используют один `umbra.library`. Выход очищает профиль, но не библиотеку. При следующем входе локальная библиотека объединяется с удалённой и весь результат загружается под новым UID.

Сценарий: A оставляет заметки → выходит → B входит в том же браузере → B видит записи A, а доступные для записи записи отправляются в облако B. Это происходит и при корректных правилах Firestore: приложение само записывает данные с полномочиями B. Ошибка с `undefined` может мешать части записей, но не устраняет дефект; JSON-сериализация локального кэша уже удаляет такие свойства.

**Исправление:** хранилище по UID, отдельная гостевая библиотека, немедленная смена отображаемого набора при смене пользователя. Перенос гостевой библиотеки — отдельное понятное действие. Очереди и ответы запросов должны быть привязаны к UID и поколению сессии. Не назначать существующий общий кэш автоматически первому вошедшему пользователю: его происхождение неизвестно.

## 2. Добавление на полку не сохраняется в облако

**Код:** `src/pages/Title.tsx:109–120`; `src/lib/cloud.ts:38–39`; `src/state.tsx:123–124`.

`setStatus` явно добавляет `season` и `episode` со значением `undefined`. `pushItem` отправляет объект без преобразования; Firestore по умолчанию отвергает такие поля. Ошибка подавляется, локальное состояние обновляется успешно.

**Исправление:** явный сериализатор разрешённых полей, исключающий отсутствующие опциональные свойства, плюс проверка структуры перед записью. Различать «не передано» и «нужно удалить существующее значение». Показывать сохранение и ошибку; не считать наличие UID доказательством успешной синхронизации.

Поведение SDK подтверждено локально и описано в [FirestoreSettings](https://firebase.google.com/docs/reference/js/firestore.firestoresettings#firestoresettingsignoreundefinedproperties).

## 3. Интерфейс показывает вход без действующей сессии

**Код:** `src/lib/auth.ts:30–60, 67–76`; `src/pages/Login.tsx:8–9`; `src/pages/Cabinet.tsx:7–18`.

UI определяет вход по `umbra.account`, а облако — по `firebaseAuth.currentUser`. В обработчике Firebase отсутствует очистка аккаунта при `user = null`. После потери сессии профиль остаётся, `/login` перенаправляет в кабинет, а UID может отсутствовать.

**Исправление:** один AuthProvider с состояниями `initializing`, `authenticated`, `anonymous`, `error`. Пользователь определяется Firebase observer; сохранённый профиль годится только как необязательный кэш отображения. Маршруты ждут окончания инициализации. Все подписчики используют один реактивный источник.

Подмена localStorage позволяет подменить отображаемый профиль, но сама по себе не даёт права читать Firestore другого пользователя. Реальная защита данных должна обеспечиваться серверными правилами.

## 4. Синхронизация может не запуститься после перезагрузки

**Код:** `src/state.tsx:92–108`.

При старте профиль уже может быть в localStorage, а Firebase UID ещё не восстановлен. Effect выходит на проверке `!uid`. После восстановления сессии значение `account.sub` остаётся тем же — зависимость эффекта не меняется.

**Исправление:** запускать синхронизацию от подтверждённых `authStatus` и `uid`, а не от сохранённого профиля. При смене UID отменять подписку/обработку старых результатов. Проверить сценарий с намеренно замедленным восстановлением Firebase.

## 5. Google Redirect на iPhone требует пересмотра

**Код:** `src/lib/auth.ts:63–85`; `src/lib/firebase.ts`; `src/components/GoogleSignIn.tsx`.

На iOS всегда выбирается redirect. Сайт работает на `github.io`, authDomain — на `firebaseapp.com`. Firebase документирует ограничения такого механизма при блокировке стороннего хранилища. Ошибки `getRedirectResult` полностью скрываются. После полного перехода результат также не обрабатывается единым реактивным маршрутизатором входа.

**Исправление:** выбрать поддерживаемую конфигурацию из [рекомендаций Firebase](https://firebase.google.com/docs/auth/web/redirect-best-practices). Для этого небольшого приложения разумно рассмотреть Firebase Hosting на домене проекта, либо корректно настроенный собственный домен с auth helper. Если оставлять Pages — проверить поддерживаемый popup-поток на целевых устройствах. Простого изменения строки `authDomain` недостаточно.

Сохранять разрешённый внутренний return URL до redirect, обрабатывать результат и ошибку в AuthProvider, проверять точный hostname `kovalenkoserhii2107-maker.github.io` в Authorized domains. Текущее сообщение «добавь github.io» недостаточно точно. Фактическая конфигурация консоли не проверена; сбой на конкретном iPhone не воспроизведён.

## 6. Выход и регистрация скрывают частичные ошибки

**Код:** `src/lib/auth.ts:93–105`; `src/components/EmailAuth.tsx`.

Ошибка Firebase signOut подавляется, после чего UI всё равно очищает профиль. При неудаче реальная сессия может сохраниться. Ошибка updateProfile также скрывается, а UI сохраняет желаемое имя как будто обновление прошло.

Нет процесса восстановления пароля, отправки подтверждения email, обработки конфликтов способов входа. Необходимость обязательного подтверждения email — продуктовая политика; сейчас это не реализовано. Настройки защиты от перебора и перечисления email нужно проверять в Firebase.

**Исправление:** отображать фактический результат выхода, завершать пользовательские подписки, предоставлять повторную попытку. Согласовать локальный профиль с Firebase. Добавить восстановление пароля и проверенный сценарий Google/email для одного адреса; не связывать учётные записи только по совпадению строки email.

## 7. Удалённые записи возвращаются, синхронизация не непрерывная

**Код:** `src/lib/cloud.ts:33–54`; `src/state.tsx:92–129`.

Удаление физическое, а объединение сохраняет все локальные записи. Второе устройство со старой копией после очередного pull+merge+push восстановит удалённое. `getDocs` вызывается только при старте эффекта; подписки `onSnapshot` нет. Запись каждого символа заметки вызывает отдельный cloud write. Сетевые операции внутри updater `setItems` — побочный эффект в функции, которая должна быть чистой; в StrictMode возможны повторные вызовы.

**Исправление:** определить один протокол синхронизации. Например: библиотека по UID, `onSnapshot`, долговечная очередь изменений, идентификаторы операций, подтверждение записи, маркеры удаления, правила разрешения конфликтов. Серверная дата полезна, но сама по себе не решает конфликты. При использовании persistent cache Firestore учесть общие устройства и logout. Не отправлять всю библиотеку при каждом входе. Для заметок — debounce с надёжным сохранением незавершённой операции при уходе со страницы.

## 8. Правила доступа к Firestore не версионируются

В репозитории нет `firestore.rules`, `firebase.json` и тестов правил. Это не доказывает, что рабочая база открыта: правила могли быть опубликованы вручную.

**Что проверить:** доступ к `/users/{uid}` и `/users/{uid}/library/{itemId}` только при `request.auth != null && request.auth.uid == uid`; допустимые поля и типы; длина заметки; диапазон рейтинга; соответствие ID документа типу/ID записи. Клиентский `account.sub` не является доказательством полномочий.

**Исправление:** хранить правила в git и проверять Firebase Emulator Suite: гость, владелец, другой UID, некорректные документы. Публичная клиентская конфигурация Firebase сама по себе не является утечкой административного ключа.

## 9. Два механизма загрузки и публикации приложения

**Код:** `index.html:19–46`; `vite.config.ts:5–14`; `.github/workflows/pages.yml:29–50`.

Исходный HTML одновременно содержит Vite entry и ручной loader готовых assets. При сборке остаются два разных URL одного entry: с query и без него. На GitHub-hostname оба модуля могут выполниться, повторно инициализируя приложение и подписки. Это подтверждено структурой build artifact; браузерный сценарий двойного запуска отдельно не выполнялся.

Опубликованный HTML на момент запроса соответствует исходному варианту, содержит неработающий `/src/main.tsx` и не содержит manifest-ссылки из production build. Это свидетельствует о расхождении опубликованной страницы и локального `dist`; точный режим Pages в настройках не проверен.

**Исправление:** один Vite entry, один способ публикации — целиком `dist`. Удалить обходной boot, ручную версионированную CSS-ссылку и коммиты build assets обратно в main. Вернуть content hashes в имена ресурсов. После публикации проверять entry, manifest и версию. Версию релиза формировать из одного источника.

## 10. PWA отключает собственное кэширование

**Код:** `src/main.tsx:11–15`; `index.html:33–40`; `src/pages/Settings.tsx:32–43`; `vite.config.ts`.

Service worker генерируется, но автоматическая регистрация отключена; стартовый код удаляет регистрации и все Cache Storage на origin. На GitHub Pages другие проекты этого владельца делят origin, поэтому очистка может затронуть их кэши и service workers. Заявленного в README runtime-кэширования TMDB и постеров в конфигурации нет.

**Исправление:** единая регистрация SW, ограниченная область `/umbra/`, удаление только собственных устаревших кэшей при миграции, осмысленная политика обновления. Установка на домашний экран и работа offline — отдельные свойства; проверить оба. Кнопку «Установить» показывать только когда доступен соответствующий сценарий: сейчас без `deferred` её обработчик ничего не делает.

## 11. Слишком много запросов, нет общей политики восстановления

**Код:** `src/components.tsx:81–87`; `src/lib/ratings.ts`; `src/lib/tmdb.ts`; `src/lib/catalog.ts`; `src/lib/tv.ts`; `src/components/Seasons.tsx`.

Каждая карточка запускает получение внешнего ID и рейтинга независимо от видимости. Главная отображает несколько полных рядов, а IMDb-подборки дополнительно делают до 20 find-запросов каждая. Для сезона выполняется запрос ID для каждой серии. Общего ограничения конкуренции, timeout/abort и retry-политики нет. В ratings существует дедупликация по одному title, но она не ограничивает количество разных title.

**Исправление:** единый API-клиент, timeout и AbortSignal, ограниченный retry для временных ошибок с учётом 429, кэш с TTL, лимит параллельных запросов, рейтинги видимых карточек и пакетная загрузка. Отделить необязательные рейтинги/людей от основного каталога, чтобы сбой одного сервиса не ломал весь экран. Измерить количество запросов и длительность загрузки до/после. Разделить JS на маршруты после исправления двойного boot.

## 12. Гонки и некорректные данные на экранах

- `src/pages/Search.tsx:61–75`: loadMore не привязан к версии запроса. При смене q/фильтров старый ответ может дописаться в новый список. Нужен query key/generation и отмена запросов.
- `src/pages/Search.tsx`: когда фильтры скрыли все загруженные результаты, кнопка следующей страницы тоже исчезает. Подходящие записи на следующих страницах становятся недоступны. Пагинация должна оставаться доступной независимо от количества видимых записей.
- `src/pages/Title.tsx:67–80`: IMDb rating не сбрасывается при смене тайтла, старый async-ответ не блокируется. Может отображаться рейтинг предыдущего фильма.
- `src/pages/Title.tsx:103`: fallback на US отображается под заголовком выбранного региона, например UA. Убрать молчаливую замену либо подписывать фактический регион.
- `src/lib/tmdb.ts:imdbChart`: при ошибке внешнего IMDb-сервиса возвращается topRated TMDB под прежним названием IMDb. Показывать настоящий источник и состояние fallback.
- `src/pages/Feed.tsx`: ошибки после первой страницы почти не видны; observer может продолжать увеличивать номер страницы после неудачи. Повторять текущую страницу по явной retry-политике; сбрасывать error при смене ленты.
- `src/lib/search.ts`, `src/pages/Guide.tsx`: единый список movie genre IDs применяется также к TV. Развести справочники и отображаемое соответствие жанров.
- `src/App.tsx`: добавить маршрут неизвестного адреса; валидировать ID и тип параметров до API-вызова.

## 13. Импорт и localStorage недостаточно защищены от повреждений

**Код:** `src/state.tsx:33–58, 82–89, 132–135`; `src/pages/Settings.tsx`.

Импорт проверяет только Array.isArray. Например, `{ "items": [null] }` проходит импорт и затем ломает обращения к полям записей. Список полностью заменяется, настройки из экспортированного файла не восстанавливаются, импорт не отправляется в облако сразу. При следующем merge удалённые элементы могут вернуться.

Часть обращений к localStorage без try/catch, включая обращение при загрузке модуля до установки React Boundary. Недоступность хранилища или переполнение могут сорвать запуск/сохранение.

**Исправление:** versioned schema, runtime-валидация, лимит размера/числа записей, дедупликация, превью merge/replace, резервная копия до замены. Импорт должен проходить через тот же протокол синхронизации. Централизовать работу с хранилищем и показывать невозможность сохранить. Для полки и очереди предпочтительно асинхронное хранилище IndexedDB.

## 14. Инженерная проверяемость

Нет lock-файла, тестовых команд, lint-команды и проверок pull request. CI использует npm install, поэтому дерево зависимостей меняется между сборками. strict TypeScript не включён. README описывает хранение только на устройстве и ввод TMDB key в настройках, хотя есть облачный слой, встроенный ключ, а поля ввода ключа в Settings нет.

**Исправление:** зафиксировать lock и версию Node, npm ci, PR-проверки типов/тестов/сборки. Постепенно включить strict. Добавить диагностику auth, sync, API и bootstrap с номером релиза, без токенов, паролей и содержимого личных заметок. Обновить документацию и тексты «только на этом устройстве»/«синхронизируется» по фактическому состоянию.

## Целевой процесс авторизации

1. Инициализация Firebase и выбранного persistence с наблюдаемой ошибкой.
2. AuthProvider сообщает initializing; защищённые экраны ждут.
3. Observer подтверждает пользователя или гостя; кэш профиля не решает состояние входа.
4. Login/Google/redirect завершаются в одном состоянии AuthProvider; ошибка видна пользователю.
5. Для подтверждённого UID подключается только его библиотека и очередь изменений.
6. Sync показывает loading, pending, synced, offline или error по реальным результатам.
7. Logout закрывает подписки, изолирует библиотеку и подтверждает завершение сессии.

## Порядок реализации

**Первый этап — сохранность данных:** изоляция по UID и безопасная миграция старого кэша; единый auth state; исправление undefined; видимые ошибки; проверка Firestore rules.

**Второй этап — предсказуемый запуск:** один entry и один dist-deploy; hashes; lock + npm ci; корректный redirect/Google flow; PWA без глобальной очистки.

**Третий этап — синхронизация:** подписки, долговечная очередь, маркеры удаления, конфликты, безопасный импорт, подтверждённые статусы.

**Четвёртый этап — скорость и поддержка:** API-клиент, ограничение запросов рейтингов, устранение гонок, разделение bundle, диагностика, документация.

## Приёмочные сценарии

1. Перезагрузка с действующей сессией и задержанным Firebase restore запускает sync ровно для правильного UID.
2. Сохранённый профиль + Firebase null переводят UI в гостевой режим.
3. A → logout → B не показывает и не копирует данные A; проверить также две вкладки.
4. Добавление фильма без season/episode получает подтверждение облачной записи.
5. Смена пользователя во время pull/write не применяет результат к другой библиотеке.
6. Удаление на первом устройстве не восстанавливается со второго, в том числе после offline.
7. Offline-изменение переживает закрытие страницы и успешно отправляется после возвращения сети.
8. Отказ rules/quota/storage отображается как ошибка, а не как успешная синхронизация.
9. Вход Google проходит в обычном Safari и установленной PWA; redirect error видна; пароль можно восстановить.
10. Некорректный импорт не меняет рабочую библиотеку; корректный импорт согласован с облаком.
11. Медленная пагинация поиска не примешивает результаты старого запроса.
12. Опубликованный релиз загружает один entry, не запрашивает /src/main.tsx, содержит manifest, не удаляет кэши других приложений.

Для тестов правил и сценариев данных использовать эмуляторы/тестовый Firebase-проект. Для OAuth необходим отдельный контроль реального браузерного сценария; unit-тесты его не заменяют.
